## 2026-09-17 tracking corrections

Fixed two adapter defects found after the first phone report:

- Set the XR8 camera origin to unit height before configuring its projection.
  The pinned engine derives responsive scale from origin.y; the previous MindAR-style
  zero origin produced a degenerate scale.
- Refresh target visibility from the pinned runtime's per-frame `detectedImages`
  snapshot. Pose-change events alone are not a tracking heartbeat: a stationary
  target could previously trigger the 900 ms loss watchdog despite still being visible.

The AR chooser now explicitly says that 8th Wall requires the supplied artwork.
Arbitrary squares, rectangles and plain tabletops are not image targets. The separate
native surface mode remains the option for supported Android surface placement.

Verification for this correction: 52 automated tests passed, including new regressions
for nonzero startup scale and stationary-target tracking; syntax and whitespace checks
passed. Installed Windows Edge was found and used with an isolated temporary profile,
without downloading a browser. The real vendored XR8 engine and image-tracking WASM
initialized in the browser. A separate browser test using simulated tracking exercised
the real Three.js scene, AR adapter, game loop and controls: stationary target retention,
snake movement and keyboard steering, loss pause, explicit resume, board rendering,
and camera-canvas cleanup all passed at a 390 × 844 browser window setting.

The first engine check still showed WAITING at a 15-second virtual-time budget; a
35-second observation completed successfully. This is a headless test observation,
not a measured phone startup time. No real camera, physical target, Android tracking
quality, or native WebXR surface was verified. No production build or deployment.
These corrections are on the prototype branch; main was independently advanced to
`b9db287` before this correction and is not modified by this fix.

## Implemented

- A separate **8th Wall · experimental** entry in the AR chooser, retaining MindAR
  card tracking, native surface AR and ordinary 3D play.
- Lazy, single-instance loading of pinned XR8. A dedicated adapter controls camera
  entry/exit, loading errors, permission denial, cancellation and recovery.
- XR8 drives the game frame loop. Its camera canvas sits behind the existing
  transparent Three.js renderer; no Three.js vendor wrapper or global THREE is needed.
  Camera projection and world pose come from XR8. The board's target transform is
  converted from XY to XZ; screen-relative steering keeps using the existing camera.
- Target loss hides the board and pauses play. Reacquisition requires explicit resume.
  A watchdog handles stalled tracking updates. Exit stops the runtime and camera,
  removes owned pipeline modules/canvas/listeners and restores 3D rendering.
- A 160 mm square printable target at `/eighth-wall-target.html`, with separate
  original artwork and data generated by the official processor. The processor's
  centered 3:4 crop covers the square's full height; board scaling uses that height.
- Exact static routes for vendor/target assets and their MIME types, preserving
  repository-file restrictions. The existing static-copy build script already copies
  these public files; it was inspected but never executed.

## Dependencies and costs actually incurred

Installed with package scripts disabled and versions pinned in package-lock.json:
`@8thwall/engine-binary@1.0.0`, `@8thwall/image-target-cli@1.0.0` and resolved
`sharp@0.34.5`. No toolchain or browser was installed; no subscription was bought.
The seven new AR/processor dependency archives total **21,835,323 bytes compressed**
(about 21.8 MB), measured from npm cache records; this excludes npm metadata and
Three.js. The runtime alone is 13,948,985 bytes compressed and about 31 MB unpacked.

The complete original runtime distribution is vendored with its license. All 13
vendored files were hash-compared with the installed distribution. Normal play
loads none of it. Experimental entry requests `xr.js` and preloads the `slam` chunk:
source inspection confirms that chunk supplies XrController even with world tracking
disabled. Actual mobile network transfer, optional resource requests and GPU/memory
costs have not been measured. The runtime persists in memory for re-entry; camera
and session-owned resources are stopped on exit.

The binary retains its limited-use license and notices; the app and printable page
link the agreement and warranty disclaimer. The processor is MIT and is used as a
development dependency, not a browser dependency.


For an Android camera trial, use Chrome USB remote debugging and port forwarding:
connect the phone with USB debugging enabled, open `chrome://inspect/#devices` on
the computer, enable port forwarding for device port `5174` to `localhost:5174`,
then open `http://localhost:5174/` in Chrome on the phone. The computer's Chrome
must first be able to reach the WSL development server at that address. See
[Chrome's local-server guide](https://developer.chrome.com/docs/devtools/remote-debugging/local-server/).
A plain LAN HTTP address is not a substitute for secure localhost/HTTPS camera access.
Alternatively use an already authorized HTTPS preview; this change does not publish one.

Choose **Play in AR → 8th Wall · experimental**, allow the camera, and point at the
printed artwork. Press Play once found. The launch link on the printable page opens
its own preview origin; no QR for the submitted site is used because that site does
not contain this experiment.

## Regenerate the target

```sh

```

This is a short local image-processing command, not an application build. It creates
the SVG/PNG artwork and invokes the pinned official processor's `applyCrop` with its

outputs together; do not reuse MindAR target data. The SVG embeds the repository's
existing approved logo. Generated artwork was visually inspected, but tracking
feature quality has not been measured.

## Dependency decision

Use the prebuilt `@8thwall/engine-binary@1.0.0` as the proposed prototype runtime,
with `@8thwall/image-target-cli@1.0.0` for a separately generated image target.
Both exact versions were confirmed through npm metadata. No package was installed.

The [MIT engine source](https://github.com/8thwall/8thwall/blob/main/packages/engine/README.md)
currently directs users to the distributed binary for easiest integration; its
source distribution requires a Bazel/WASM build. Do not take that build route
under the user's no-build instruction. The
[official loading guide](https://8thwall.org/docs/engine/overview) supports a static
script and adjacent runtime resources without a platform account or project key.
Use a pinned local distribution, lazy-loaded on experimental AR entry.

The binary is **not MIT**. Retain its original distribution notices and the
[XR Engine license](https://github.com/8thwall/engine/blob/main/LICENSE), including
creator, copyright, agreement and warranty-disclaimer attribution. The target
processor is MIT; preserve its notice if redistributed. This decision does not
extend scope to world tracking, purchases or publication.

## Integration findings and remaining checks

The [current official examples](https://github.com/8thwall/8thwall/blob/main/examples/README.md)
list a Three.js world-effects example and an A-Frame image-target example. They do
not list a current minimal Three.js image-target example. The
[Three.js example](https://github.com/8thwall/threejs-world-effects-example)
uses Three.js `^0.183.2`, assigns `window.THREE`, then configures XR8 camera pipeline
modules. Our app pins `0.185.1`; compatibility is plausible but unverified.

The existing scene owns its renderer and camera; `getXRContext()` exposes them.
`enterAR()`, `setARProjection()`, `trackAR()` and `exitAR()` support the existing
adapter. In contrast, the example's `XR8.Threejs.pipelineModule()` creates its own
scene/rendering environment. Before implementation, choose a custom pipeline for
the existing renderer or explicitly transfer board rendering into the XR8 scene.
Do not start two render loops or pass a world-space pose into the current
camera-relative MindAR path. Verify projection, coordinate conversion, orientation
and target scale on device.

[XR8 lifecycle documentation](https://8thwall.org/docs/api/engine/xr8) distinguishes
pause from stop; use stop on exit to close the camera. Cancellation during loading
and permission grants must prevent late starts; remove owned pipeline callbacks
and restore ordinary 3D. Preserve current main.js tracking-loss pause and explicit
resume behavior. HTTPS camera access and an actual Android camera test remain
required.

The local server currently rejects nested vendor directories and JSON assets.
After acquiring the distribution, add a narrow explicit manifest for its required
paths, with JavaScript/JSON/image MIME types and any proven additional binary types.
Keep repository-file and symlink protection. The existing build script already
copies `public/` recursively; inspection alone was sufficient here, and it was not run.

network transfer and disk usage apply. No duration is promised.

After Phase 2 creates and reviews the square artwork, invoke the installed CLI:

```sh
./node_modules/.bin/image-target-cli
```

Follow its prompts for source image, planar geometry, crop, target name and output
folder. The [processor documentation](https://github.com/8thwall/8thwall/blob/main/apps/image-target-cli/README.md)
specifies JSON plus image outputs; load the JSON through `imageTargetData` and make
its `imagePath` resolve to the served target image. Native modules should fetch
JSON rather than copying example bundler `require()` calls. A MindAR `.mind` file
is incompatible. Physical print dimensions and a launch QR remain Phase 2 work.
